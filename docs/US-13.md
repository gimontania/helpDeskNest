# US-13 · Cambiar el estado de un ticket

## Endpoint

PATCH /tareas/:id/estado requiere Authorization: Bearer <JWT>, un id UUID válido y este cuerpo:

```json
{ "estado": "EN_PROCESO" }
```

Devuelve 200 y el ticket actualizado. Prisma actualiza automáticamente actualizadoEn. No requiere cambios del esquema ni una nueva migración.

## Permisos y transiciones

ADMIN y AGENTE pueden cambiar el estado de cualquier ticket, en coherencia con la visibilidad interna actual del módulo. EMPLEADO no puede cambiar estados, aunque sea creador del ticket. Esta política debe ser acordada por el equipo antes de fusionar el PR.

Se adopta el flujo secuencial del curso:

| Estado actual | Único siguiente estado |
| ------------- | ---------------------- |
| ABIERTO       | EN_PROCESO             |
| EN_PROCESO    | RESUELTO               |
| RESUELTO      | CERRADO                |
| CERRADO       | Ninguno                |

Se rechazan saltos, retrocesos, repetir el mismo estado y reabrir un ticket cerrado. No se exige asignación para esta historia; la asignación pertenece a otra funcionalidad.

## Errores

| Código | Motivo                                         |
| ------ | ---------------------------------------------- |
| 400    | UUID inválido, estado ausente o fuera del enum |
| 401    | JWT ausente, inválido o vencido                |
| 403    | Rol sin autorización                           |
| 404    | Ticket inexistente                             |
| 409    | Transición prohibida o cambio concurrente      |

Una transición prohibida indica el estado actual, el solicitado y el siguiente permitido. Para un ticket cerrado explica que no puede cambiar de estado. La actualización incluye el estado previamente leído en la condición SQL para no sobrescribir otro cambio concurrente.

## Demostración

1. Crear un ticket mediante POST /tareas; inicia ABIERTO.
2. Con JWT de AGENTE o ADMIN, avanzar EN_PROCESO, RESUELTO y CERRADO usando PATCH.
3. Intentar volver de CERRADO a ABIERTO: 409 con mensaje claro.
4. Intentar saltar de ABIERTO a RESUELTO: 409.
5. Intentar el cambio con EMPLEADO: 403; sin token: 401.
6. Enviar estado inexistente: 400; UUID válido sin ticket: 404.

## Arquitectura y pruebas

Se mantiene TareasModule con su Controller y Service. El DTO valida el enum, los Guards verifican JWT y rol, y el Service aplica las reglas de negocio. No se crean tablas de permisos ni frontend.

```bash
pnpm exec prisma generate --config prisma7.config.ts
pnpm test -- --runInBand src/tareas
pnpm build
```

Las pruebas del servicio cubren las 16 combinaciones de estados y conflictos concurrentes. Las pruebas HTTP utilizan JWT y Guards reales con el servicio simulado. No sustituyen una demo contra PostgreSQL real.
