# US-14 · Asignar un ticket a un agente

## API

PATCH /tareas/:id/agente con Authorization: Bearer <JWT de ADMIN>:

```json
{ "agenteId": "a7106e10-ecfa-4c3a-9089-d0581e68a540" }
```

Devuelve 200 y el ticket actualizado, incluyendo el agente con id, nombre, email y rol; nunca incluye su contraseña ni su hash.

## Política de asignación

- Solo ADMIN puede asignar y reasignar tickets.
- AGENTE no puede tomar tickets para sí mismo ni asignarlos a otra persona.
- EMPLEADO no puede asignar tickets, aunque sea su creador.
- El destinatario debe existir y tener exactamente rol AGENTE; ADMIN no es un destinatario válido.
- Se permite reasignar y repetir la asignación al mismo agente.
- La asignación modifica agenteId y la fecha de actualización automática de Prisma; no modifica el estado ni otros datos del ticket.
- Esta historia permite asignar en cualquier estado. No agrega reglas de transición ni permite desasignar mediante null.

El equipo debe confirmar esta política antes de fusionar. Sigue la historia «Como administrador» y mantiene los roles directos del curso, sin tablas de permisos.

## Errores

| HTTP | Motivo                                                               |
| ---- | -------------------------------------------------------------------- |
| 400  | UUID inválido, agenteId ausente o usuario con rol distinto de AGENTE |
| 401  | JWT ausente, inválido o vencido                                      |
| 403  | Solicitante distinto de ADMIN                                        |
| 404  | Ticket inexistente o usuario inexistente, con mensajes diferenciados |

## Arquitectura y demo

Se conserva TareasModule con TareasController y TareasService. El DTO valida UUID; JwtAuthGuard y RolesGuard protegen el endpoint; el Service comprueba existencia y rol y utiliza Prisma/PostgreSQL. No necesita migración: agenteId ya existe en el esquema.

Para la demo: obtener JWT de ADMIN, listar agentes con GET /usuarios?rol=AGENTE, crear un ticket y asignarlo con PATCH. Consultar GET /tareas/:id para comprobar el responsable. Probar además un usuario inexistente, un EMPLEADO como destinatario y una solicitud con JWT de AGENTE.

```bash
pnpm exec prisma generate --config prisma7.config.ts
pnpm test -- --runInBand src/tareas/asignar-agente
pnpm build
```

Las pruebas utilizan Prisma simulado; las pruebas HTTP ejecutan JWT, Guards y validación reales. La demo sobre PostgreSQL real queda a cargo del equipo.
