# US-22 · Datos de prueba para la demo

El seed carga 3 usuarios (uno por rol), 3 categorías (Hardware, Accesos, Redes), 4 tickets (uno en cada estado) y 8 comentarios (dos por ticket, de empleado y agente).

Los tickets pertenecen al empleado de prueba. El ABIERTO queda sin asignar; los otros tres se asignan al agente. Las cuatro prioridades también están representadas.

## Ejecución sobre una base nueva

Configurar DATABASE_URL en .env apuntando a PostgreSQL de desarrollo. Primero aplicar el esquema a la base vacía y después cargar el seed:

```bash
pnpm install --frozen-lockfile
pnpm exec prisma generate --config prisma7.config.ts
pnpm exec prisma migrate deploy --config prisma7.config.ts
pnpm exec prisma db seed --config prisma7.config.ts
```

No requiere nuevas migraciones. Se aprovechan las relaciones y enums del esquema existente.

## Acceso de prueba

| Rol      | Correo                 | Contraseña  |
| -------- | ---------------------- | ----------- |
| ADMIN    | admin@helpdesk.test    | Password123 |
| AGENTE   | agente@helpdesk.test   | Password123 |
| EMPLEADO | empleado@helpdesk.test | Password123 |

Las contraseñas se almacenan como hash bcrypt. Configurar JWT_SECRET para levantar la API e iniciar sesión mediante POST /auth/login.

Se puede repetir el seed sin duplicar sus registros: usuarios y categorías usan claves únicas; tickets y comentarios usan UUID fijos. Reejecutarlo restaura los datos de demostración y las contraseñas de esas cuentas. No elimina otros registros. Usar únicamente en una base de desarrollo o demo.

Para comprobar: iniciar sesión con los tres roles, consultar categorías y tickets, verificar los cuatro estados y consultar los comentarios de cada ticket. Las métricas de una base recién cargada deben mostrar total 4 y un ticket por estado.

## Verificación realizada

Se probó sobre una instancia PostgreSQL 18 nueva y aislada: migrate deploy aplicó la migración inicial, el seed se ejecutó sin errores y db seed permitió repetirlo sin duplicados. Las consultas SQL confirmaron 3 usuarios (uno por rol), 3 categorías, 4 tickets (uno por estado), 8 comentarios (dos por ticket) y ninguna asignación a un usuario que no fuera AGENTE. La compilación de NestJS también pasó.
